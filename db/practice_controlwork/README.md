# Практика к контрольной PostgreSQL

Составлено 21.11.2026 по реальной схеме `db_vzhukh` базы `cu-db`. Решений нет; подсказки находятся в отдельном файле. ★ — базовое, ★★ — среднее, ★★★ — сложное. На задачу: 5–10 / 10–20 / 20–30 минут соответственно.

## Как работать безопасно

Исследование базы выполнено по SSL в транзакции только для чтения: SELECT, information_schema и настройки сеанса. Реальные таблицы не изменялись. Не меняй также существующие `*_test_*`, `*_homework_*` и `active_courier_test_8`: это не наши песочницы.

Для задач 1–10 открывай `BEGIN READ ONLY`, затем выполняй `SET LOCAL search_path TO db_vzhukh, public` и `SET LOCAL timezone TO 'Europe/Moscow'`; заверши `ROLLBACK`. Если соединение идёт через пул, настройки нужно задавать внутри каждой транзакции. При необходимости используй полные имена `db_vzhukh.orders` и т. п.

Для задач 11–25 выполни `sandbox.sql` целиком и решай задачу **в той же открытой транзакции и на том же соединении**, после чего обязательно `ROLLBACK`. Затем для следующей задачи запускай подготовку заново. Файл создаёт только временные таблицы. После подготовки `search_path` начинается с `pg_temp`; в изменяющих запросах всё равно явно пиши `pg_temp.lab_stock` и другие учебные имена. Не запускай подготовку через обёртку, автоматически делающую COMMIT после каждого вызова: используй один cursor/одно закреплённое соединение либо локальную PostgreSQL. При transaction pooling нельзя рассчитывать на сохранение временных объектов после завершения транзакции.

В двухсеансовой задаче 20 используй только отдельную локальную учебную базу. Временные таблицы разных сеансов друг другу не видны.

Статусы заказов: `created` — 2, `assembling` — 7, `delivering` — 8, `cancelled` — 3, `delivered` — 30. Роли сотрудников: `picker`, `courier`. Города: Москва, Санкт-Петербург, Екатеринбург. `created_at` заказов: 01.07–09.08.2026 по Москве. У 12 заказов нет курьера; у 10 `delivered_at > promised_at`. У 8 SKU несколько версий цены, открытых версий всего 40. SKU 1 — «Молоко питьевое 3.2%, 900 мл», открытая цена 82.00 с 01.05.2026. Для лабораторного резервирования `qty_available` означает свободный остаток: резерв уменьшает его и увеличивает `qty_reserved`. Это правило упражнения, а не установленная семантика исходной системы. Время — Europe/Moscow; интервалы цен трактуем как `[valid_from,valid_to)`, NULL справа означает бесконечность. Пустой результат допустим, если запрос корректен.

## 1. Подзапросы

**1. ★ Заказы выше среднего.** Выведи `order_id,total_amount` доставленных заказов, сумма которых строго выше среднего по всем доставленным заказам. Используй скалярный подзапрос. Сортировка: сумма убывает, ID возрастает.

**2. ★ Покупатели без доставки.** Через `NOT EXISTS` найди покупателей, у которых нет ни одного доставленного заказа, включая покупателей совсем без заказов. Вывод: `customer_id,full_name`, по ID. Объясни, почему здесь опасен `NOT IN`, если подзапрос может вернуть NULL.

**3. ★★ Выше среднего своего склада.** Для каждого доставленного заказа проверь, больше ли его сумма среднего доставленных заказов того же `darkstore_id`. Используй коррелированный подзапрос. Выведи заказ, склад, сумму и среднее склада. Среднее включает сам заказ.

**4. ★★ Товары, которые никто не собрал.** Найди товары, для которых нет позиции доставленного заказа с `qty_collected > 0`. Выведи `sku_id,name`; учти товары вообще без позиций. Не используй оконные функции.

**5. ★★★ Покупатель охватил все категории.** Найди покупателей, у которых среди собранных товаров доставленных заказов есть каждая категория, встречавшаяся хотя бы в одном доставленном заказе с `qty_collected > 0`. Используй двойной `NOT EXISTS`. Если множество категорий пусто, по условию подходят все покупатели. Вывод: `customer_id`.

## 2. Оконные функции

**6. ★ Номер заказа покупателя.** Для всех заказов выведи `customer_id,order_id,created_at` и порядковый номер заказа внутри покупателя. При одинаковом времени порядок определяется `order_id`. Финальная сортировка: покупатель, время, ID.

**7. ★★ Топ-3 товара категории.** Посчитай собранное количество каждого товара в доставленных заказах и выбери первые три места внутри категории через `DENSE_RANK`. Товары без таких продаж не включай; равные количества получают одно место, поэтому строк может быть больше трёх. Выведи категорию, SKU, количество, место.

**8. ★★ Накопительная выручка.** Сначала получи дневную выручку каждого склада по московской дате создания заказа, затем накопительную сумму внутри склада. Вывод: склад, день, дневная и накопленная выручка. Дни без доставленных заказов не добавляй. Укажи оконную рамку явно.

**9. ★★ Предыдущий заказ.** Для каждого заказа выведи время предыдущего заказа того же покупателя и интервал между ними. Порядок — `(created_at,order_id)`. У первого заказа оба вычисленных значения NULL. Статусы не фильтруй.

**10. ★★★ Скользящее среднее по календарю.** Построй для каждого склада календарь 01.07–09.08.2026, заполни отсутствующую дневную выручку нулями и вычисли среднее за текущий и шесть предыдущих календарных дней. До 07.07 используй только дни, имеющиеся с начала календаря. Выведи склад, день, выручку, среднее. Объясни, почему семь строк исходной разреженной агрегации не равны семи дням.

## 3. Представления и SCD-версионность

**11. ★ Временное представление доставки.** Создай `CREATE TEMP VIEW lab_delivery_report` по реальным `orders`, `darkstore`, `city`. Поля: `order_id,darkstore_name,city_name,total_amount,delay_minutes`. Только доставленные заказы; задержка — положительная часть разницы `delivered_at-promised_at` в минутах, NULL доставки сохраняй как NULL. Сравни количество строк с числом доставленных заказов. Объясни отличие VIEW от MATERIALIZED VIEW и почему обновление такого отчётного представления может быть неоднозначным.

**12. ★★ Цена на момент.** По `lab_price` найди цены, действовавшие на `2026-07-15 12:00:00+03`. Вывод: SKU, цена, начало и конец. Не скрывай ошибки истории через LIMIT/DISTINCT: если интервалов несколько, покажи все. Отдельно выведи товары из `product` без подходящей цены.

**13. ★★ Проверка SCD2.** Найди в `lab_price`: несколько открытых версий одного SKU; интервалы с `valid_to <= valid_from`; пересекающиеся интервалы одного SKU. У смежных интервалов общая граница не является пересечением. Пары пересечений показывай однократно по `price_id`. Отдельно найди разрывы между последовательными версиями. На исходной копии некоторые проверки могут вернуть ноль строк.

**14. ★★ Изменение цены SCD2.** Для SKU 1 установи цену 90.00 с `2026-09-01 00:00:00+03` в `lab_price`: закрой прежнюю открытую версию и добавь новую. Старую цену сохрани. После изменения на один SKU должна приходиться одна открытая версия; на самой границе выбирается новая цена. Повторное применение того же события должно ничего не менять. Все изменения — только `pg_temp.lab_price`.

**15. ★★★ Историческая сверка заказа.** Для каждой позиции реального `order_item` подбери версию `lab_price` на `orders.created_at`. Выведи `order_item_id`, зафиксированную цену позиции, историческую цену и разность. Сохрани позиции без версии; отдельно отметь 0, 1 или несколько совпадений. Не используй текущую цену вместо исторической. Объясни, почему различие цен само по себе не доказывает ошибку данных.

## 4. Транзакции

**16. ★ Откат резерва.** В `lab_stock` для `(darkstore_id,sku_id)=(1,1)` зарезервируй 3 единицы по лабораторному правилу. Сравни значения до и после UPDATE, затем выполни ROLLBACK. Объясни, почему после полного отката сама учебная таблица исчезла и как снова проверить исходное значение SELECT-запросом к реальной `stock`.

**17. ★★ SAVEPOINT и ошибка.** Создай SAVEPOINT, успешно зарезервируй 2 единицы, создай второй SAVEPOINT и попробуй установить `qty_available=-1`. Получи ошибку CHECK. Восстанови работоспособность транзакции через `ROLLBACK TO` второго SAVEPOINT; убедись, что первый резерв сохранился. В конце полный ROLLBACK. Объясни, почему SELECT до восстановления после ошибки не выполняется.

**18. ★★ Перенос остатков.** В `lab_stock` перенеси 5 свободных единиц SKU 1 со склада 1 на склад 2. Убедись, что обе строки существуют, исходного остатка хватает, сумма свободных остатков этих строк сохраняется, резерв не меняется. Смоделируй ошибку между двумя UPDATE и откати весь перенос через SAVEPOINT. Частичный перенос недопустим.

**19. ★★ Условный атомарный резерв.** Для `(1,1)` попробуй зарезервировать 100000 единиц одним условным UPDATE с RETURNING. Ожидается ноль изменённых строк. Затем зарезервируй 1 единицу; ожидается одна строка. Объясни преимущество проверки остатка в самом UPDATE перед отдельной проверкой SELECT и последующим безусловным UPDATE.

**20. ★★★ Два сеанса — только локально.** В отдельной локальной учебной PostgreSQL создай обычную таблицу `lab_concurrency_stock` с одной строкой `(id=1,qty=10)`. В двух сеансах при READ COMMITTED воспроизведи потерю обновления: оба прочитали 10, оба записали заранее вычисленное 7 после ожидания блокировки. Затем верни 10 и повтори с `UPDATE ... SET qty=qty-3 WHERE qty>=3`: результат 4. Третий вариант — SELECT FOR UPDATE и вычисление после получения блокировки. Запиши последовательность шагов A/B, места ожидания, итог и объяснение снимков. Уборку локальной таблицы выполняй только в этой отдельной базе. На удалённой cu-db эту задачу не запускай; если локальной базы нет, составь расписание на бумаге.

**24. ★★★ SCD2-функция.** Создай `pg_temp.lab_set_price(p_sku_id integer,p_price numeric,p_at timestamptz) RETURNS boolean`, работающую только с `pg_temp.lab_price`. ## Самопроверка без решений

Для каждого запроса проверь: один ли ряд соответствует требуемому объекту; не размножает ли JOIN суммы; что происходит с NULL, равными значениями и пустыми выборками; задан ли порядок; верны ли границы времени. Для изменений сравни состояние до/после и после отката. Для SCD отдельно проверь момент за микросекунду до границы, саму границу и момент после неё.

Мини-контрольная на 90 минут: 3, 7, 12, 17, 22. Дополнительный сложный вариант: 5, 10, 13, 19, 25. Сначала решай без `hints.md`.
